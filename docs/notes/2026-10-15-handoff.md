## What the game and the saves told us

- **Global enchantments set by hand work**: they show in the Magic screen's overland list, survive End Turn and are charged upkeep (evidence: the mompy project's
  `docs/reference/globals.md`, not retested here). **Time Stop is the exception**: the flag alone only draws the icon and charges mana; the real spell keeps its state somewhere not found. Mirror's byte index is mompy's number minus one.
- **A per-player hero table sits at the very start of the save**: 6 players x 35 heroes x 12 bytes, indexed by unit type (casting skill, four spell numbers, ability bits not decoded, an i16 that is -20 for a hired hero). Details in the reference doc and STORY-052.
- **An empty hero slot or vault place is -1** (a zeroed fixture reads as item 0 or unit 0: build test saves with -1s).
- **A lair's `+18/+20/+22` are not item indexes**: 22 saves hold 360 to 2400 there, never 1 to 137. *Guess:* the worth of the item rolled at clearing. The lair panel now says "to roll (value N, a guess)".
- **An item's movement byte is in half points** (8 in the save is the screen's +4): confirmed on the Items screen (STORY-055). The other stat bytes are plain; the limits the editor uses are the premade table's maxima.
- **The item info box shows at most five lines**; a sixth power is there but not drawn. Seen with a Haste that only appeared once a line was freed.
- **The game accepts an item whose power does not fit its type** (a Flaming shield) and an item in a place of the wrong kind (an armor in a misc place): loaded, drawn and kept through End Turn. Not tried: what such an item does in a fight.
- **A hero's three places have slot types** (1 melee weapon, 2 bow, 4 staff or wand, 5 armor, 6 misc; Sir Harold: 1, 5, 6) and an item has a slot code. The editor refuses a mismatch (Kevin: keep refusing for now), the game does not care.
- **Two copies of `ITEMPOW.LBX` exist** (`~/DOS/MAGIC` and `~/DOS/MagicCom`) differing in five stat records; names and masks agree. The GOG copy of the small ITEM* files is not on this machine, so the manifest entry has no hash (imports report it as unverified).

## How the real-game checks were run this time

DOSBox was started from the repo (`bash scripts/live_session.sh start`: research build, writes on, 6500 cycles) and Kevin did the clicking: start the game, Load Game, Armies > Items, right-click an item for its info.
Everything else was done through the API:

1. Back up the target slot to `~/.mirror/dev/DOSbox/backups/` first. Slot 8 was the test slot all day; **it now holds the item-move test save** (backups: `SAVE8-pre-itemedit-2026-10-15.GAM` is the original slot 8, `SAVE8-pre-itemmove-2026-10-15.GAM` the item-edit test).
2. Build the test save from `~/DOS/MAGIC/SAVE2.GAM` through the app's own functions and diff it against SAVE2 (37 bytes for the item edit, 5 for the moves).
3. Read the game's memory back: item block at `0x87F70` (6900 bytes), wizard records at `0x328BA` (hero list at `+0x76`, vault at `+0x120`). Screenshots: `POST /api/v1/capture/screenshot?inline=1`.
4. A live write is `PUT /api/v1/memory/<decimal address>` with an `If-Match` header (the base64 of the bytes expected there); a mismatch is refused. Used twice, memory only, and put back.
5. Checkpoint each step (`bash scripts/live_session.sh cp "name" "note"`): vault collection `mom-live-2026-10-15`, checkpoints 110 to 121, each with a screenshot.
6. Stop DOSBox when done (`lsof -iTCP:8086`, kill the process); it was started from this session.
