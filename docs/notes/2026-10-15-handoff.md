## Decisions Kevin made today (keep to them)

- **No giving or moving things between wizards.** Every wizard has a page, so a copy of an artifact or a new hero is made on that wizard's page from the drop-down.
- **No dismissing heroes** (do it in the game) and **no overwriting an existing hero** (levels, gear). Adding a new hero to an empty place is fine.
- The editor keeps **refusing an item in a place of the wrong kind** (the game accepts it, nothing is known about what it does in play).
- New game files go in the manifest with his say-so (he agreed to `ITEMPOW.LBX` and `ITEMDATA.LBX`; both have no hash).
- A lair's three numbers after the item count are **not** item values (see below): Kevin's reading that they are loot quality was tested and did not hold.

## What the game and the saves told us

- **Global enchantments set by hand work** (mompy's `docs/reference/globals.md`); **Time Stop is the exception** and is not editable. Mirror's byte index is mompy's number minus one.
- **Heroes.** A per-player table at the start of the save (6 x 35 x 12 bytes, by unit type) holds casting skill, four spells, ability bits (not decoded) and a first word that kazzmir calls `Level`: **-20 for a hired hero**. The hero list (`+0x76` of the wizard record) has an empty slot as unit **-1**, but its three item places read **0** there, so
  counting references must skip empty slots. A new hero is a unit record at the end of the unit table, a list entry, the -20 word and, for the player only, the **hero-name table at the end of the save** (35 x 14-byte name + experience). **The slot kinds per hero** (fighter 1,5,6; mage 4,6,6; archer 2,5,6; any weapon 3,5,6) are in `HeroTypes`, from kazzmir and checked against 15 hero types in the saves.
  New heroes appear on the wizard's summoning circle. **The game makes a new hero level 1 with experience 1**, resets the draw order of units sharing a tile, and at End Turn **compacts the unit table and renumbers the hero list** to match.
- **Items.** The item block, its movement in **half points** (confirmed by the Items screen and by kazzmir's `Movement/2`), the premade table `ITEMDATA.LBX` (250 records, movement as shown, so `save_record/1` doubles it), and the game's rules found by clearing lairs:
  **the premade "in play" flags are the 250 bytes before the 35 hero names at the very end of the save** (1 = already made; the game sets one for every item it makes); the game puts a new item in the **first record nothing points at**, and **keeps a copy in record 136**, so Mirror uses only 0 to 135.
  The item info box shows **at most five lines**. An any-weapon place (type 3: Warrax, Mystic X, Reywind) takes a melee weapon, a bow or a staff.
- **Lairs.** The **item count (`+16`) decides how many items** the game makes (1 gave one, 2 gave two, including from a Mirror-written save). The three numbers after it (360 to 2400 in the saves) **do not set the quality**: an item came with the value at 0, 100, 9000 and 30000 (costs 800, 600, 1250, 1550). Neither changes when the lair is cleared. kazzmir's own converter takes its loot budget from the guards' casting costs, not from these numbers.
  Large lairs also gave gold, mana, a spell and a prisoner hero beside the items.
- **Two copies of `ITEMDATA.LBX` and of `ITEMPOW.LBX`** (`~/DOS/MAGIC`, rewritten by the game's ITEMMAKE, and `~/DOS/MagicCom`) differ only in costs and a 6-byte tail; stat bytes and masks agree. The copies in `~/.mirror/game` are `ITEMPOW.LBX` from MAGIC and `ITEMDATA.LBX` from MagicCom.

## How the real-game checks were run this time

DOSBox was started from the repo (`bash scripts/live_session.sh start`: research build, writes on, 6500 cycles) and Kevin did the clicking: start the game, Load Game, Armies > Items, right-click an item for its info, clear a lair. Everything else was done through the API:

1. Back up the target slot to `~/.mirror/dev/DOSbox/backups/` first. Slot 8 was the test slot all day and **now holds the add-hero test save**. Backups: `SAVE8-pre-itemedit`, `-pre-itemmove`, `-pre-premade`, `-pre-flags`, `-pre-addhero` (all `-2026-10-15.GAM`; the first holds the slot's original content).
2. Build the test save from `~/DOS/MAGIC/SAVE2.GAM` through the app's own functions and diff it against SAVE2 (37, 5, 119, 72 and 136 bytes for the five tests).
3. Read the game's memory back: item block `0x87F70` (6900 bytes), wizard records `0x328BA` (hero list `+0x76`, vault `+0x120`), units `0x7E060` with the count at `0x34782`, encounters `0x86660` (24 bytes each), **premade flags `0x89AA0`**. Screenshots: `POST /api/v1/capture/screenshot?inline=1`. `mompy where pointer` names the tile or lair under the mouse.
4. A live write is `PUT /api/v1/memory/<decimal address>` with an `If-Match` header (the base64 of the bytes expected there); a mismatch is refused. Used for the lair experiments and put back where it mattered. Nothing was ever saved from the game.
5. Checkpoint each step (`bash scripts/live_session.sh cp "name" "note"`): vault collection `mom-live-2026-10-15`, checkpoints 110 to 138, each with a screenshot.
6. Stop DOSBox when done (`lsof -iTCP:8086`, kill the process).
